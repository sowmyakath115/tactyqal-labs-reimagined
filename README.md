# Tactyqal Labs — Reimagined

Independent full-stack hire-a-thon submission prototype. Not the official Tactyqal Labs website. The source brief asks for a modern homepage and a persistent blog backend with CRUD APIs. This project unifies both in a single application. Original website: https://tactyqal.com/ (reviewed November 2026). Project names and program themes are adapted from that site; artwork is CSS-based conceptual illustration, and all seeded articles are original sample content, not migrated WordPress content.

## Quick start

Requires Node.js 22.13+ (built-in `node:sqlite`; Node 22 may print an experimental warning). No external npm dependencies.

```bash
npm start
```

Open http://localhost:3000 for the homepage, http://localhost:3000/blog for the public journal, and http://localhost:3000/admin for the editorial studio. The local-only demo password is `tactyqal-local-demo`. Override it for any shared environment. Data lives in `data/blog.sqlite` and survives restarts. To reset the demo, stop the server and delete the `data` directory. Do not delete data in a deployed environment.

```bash
npm test
```

The API tests launch a separate server and temporary database. They cover seed content, search, pagination, authentication, CSRF-origin checks, validation, draft visibility, unique slugs, publishing, updating, persistence and deletion.

## Design decisions

- Parents can move from the value proposition to student examples, a four-stage roadmap, resources, FAQs and a clear contact action. Mobile navigation, visible focus states, semantic landmarks, responsive grids, reduced-motion support, and a skip link are included.
- The homepage reads published blog posts from the same backend as the public blog and admin interface; there is no separate CMS dependency.
- The database uses SQLite for a self-contained, dependency-free prototype. The schema and API boundary allow a future PostgreSQL migration. This is not a claim that SQLite is optimal for every production workload.
- Content is plain text rather than arbitrary HTML; client rendering uses `textContent` to avoid injecting stored markup. Admin sessions use random tokens and HttpOnly/SameSite cookies, origin checking for browser writes, and a basic in-memory login limiter. Production requires an explicit password and HTTPS cookies.
- Consultation uses the original public email address rather than pretending to book a real calendar appointment. The tools link points to the original site; no fake service integrations.

### API reference

| Method | Route | Access |
| --- | --- | --- |
| GET | /api/health | Public |
| GET | /api/categories | Public |
| GET | /api/posts?q=&category=&page=&limit= | Published only |
| GET | /api/posts/:slug | Published only |
| POST | /api/auth/login | Password in JSON |
| GET | /api/auth/session | Current session |
| POST | /api/auth/logout | Current session |
| GET | /api/admin/posts?q=&status=&page=&limit= | Admin |
| GET | /api/admin/posts/:id | Admin |
| POST | /api/posts | Admin |
| PATCH | /api/posts/:id | Admin; partial update |
| DELETE | /api/posts/:id | Admin |

Post fields: `title`, `slug`, `excerpt`, `body`, `category` (Ideation, Product, Launch, Technology), `status` (draft/published). IDs and timestamps are generated by the server. Slugs are unique and must contain lowercase ASCII letters, digits and hyphens. `published_at` is set on first publish and cleared when reverted to draft. Lists return `posts`, `total`, `page`, `limit`. Errors return `{error: string}` with HTTP status.

## Deployment and submission

1. Create a new GitHub repository named `tactyqal-labs-reimagined`. From this directory run:
   ```bash
   git init
   git add .
   git commit -m "Build Tactyqal homepage and blog CMS"
   git branch -M main
   git remote add origin https://github.com/YOUR-USERNAME/tactyqal-labs-reimagined.git
   git push -u origin main
   ```
2. Deploy as a Node web service on a host that supports persistent volumes (e.g., Render with a persistent disk). Set Node to 22.13+; build command `npm install` (no dependencies); start `npm start`. Set `NODE_ENV=production`, a strong `ADMIN_PASSWORD`, and `DATABASE_PATH` to a file on the persistent disk. The service reads the host's `PORT`. Use HTTPS. A free ephemeral filesystem may lose posts on redeployment; use a persistent volume or submit the local video instead. Do not deploy this SQLite implementation as a Vercel serverless function.
3. Keep the production password private; demonstrate editing in a recorded walkthrough. Do not commit credentials. Share a public homepage URL and GitHub repo URL only after testing them.
4. Record the walkthrough below if you prefer not to pay for hosting. The assignment allows a video instead of a live URL.

## 90-second walkthrough outline

- 0–20s: Explain the original split between the main site and blog. Show the redesigned hero, story cards and roadmap. Toggle to mobile width.
- 20–40s: Open the journal and show category filtering, search and an individual article.
- 40–75s: Sign in locally, create a draft, show it is absent on the public blog, publish it, reload the homepage, edit it, then delete it.
- 75–90s: Show the database schema, API tests, and README. Explain the SQLite prototype tradeoff and path to PostgreSQL.

## Limitations / next steps

No real WordPress import, rich-text editor, multi-user roles, real booking integration, production analytics, or SSR for article detail pages. Public articles use client-side rendering and should gain server-rendered metadata before a production SEO migration. Sessions and rate limits are in-memory, so they reset after restart and are intended for a single-instance demo. A production rollout should add stronger identity management, persistent session/rate limiting, backups, migration tests and monitoring. The current implementation is a focused demonstration of both requested tasks, not a production replacement.
